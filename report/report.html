1. Task 1: Object Storage and Parallel Teacher Labelling

1.1 Architecture & Local Kubernetes Setup

The project infrastructure was established on a multi-node local Kubernetes cluster deployed via k3d using configuration file cluster/k3d.yaml. The cluster consists of one dedicated control-plane server (k3d-cloud-assignment-server-0) and one agent worker node (k3d-cloud-assignment-agent-0), with ingress traffic routed through a built-in proxy load balancer mapping host port 8081 to container port 80 and host port 8444 to 443.

Object storage was provisioned by deploying SeaweedFS inside a dedicated data namespace (k8s/storage/seaweedfs.yaml). SeaweedFS provides high-throughput blob storage with an S3-compatible REST API on port 8333 backed by a 5 GiB PersistentVolumeClaim. Two S3 buckets were initialized: datasets for command corpora and teacher shards, and models for student model weights and metadata. The raw 3,000 unlabelled voice commands (data/commands_pool.jsonl) were uploaded to s3://datasets/commands_pool.jsonl.

1.2 Teacher Model & Parallel Worker Sharding

The teacher model selected was Phi-3.5-mini-instruct (3.8 billion parameters), executed locally via Ollama with strict deterministic parameters (temperature: 0, seed: 42). The system prompt engineered in prompts/teacher_prompt.txt constrains the teacher to return strictly one valid JSON object containing exactly four keys: intent, date, time, and place, adhering to the eight defined intent classes without Markdown formatting or prose commentary.

To parallelize inference across multiple cores and avoid a single-worker bottleneck, two worker jobs (teacher-worker-0 and teacher-worker-1) were executed concurrently inside the pipeline namespace. Each worker dynamically reads environment variables SHARD_INDEX and SHARD_COUNT=2, downloading commands_pool.jsonl from SeaweedFS and filtering line indices where line_number % SHARD_COUNT == SHARD_INDEX. Worker 0 processed exactly 1,500 even-indexed commands writing to datasets/teacher/shard-0.jsonl, while Worker 1 processed exactly 1,500 odd-indexed commands writing to datasets/teacher/shard-1.jsonl. Verification confirmed zero overlap between shards and complete coverage of all 3,000 command IDs with zero gaps.

2. Task 2: Training the Student (Sequence-Level Distillation)

2.1 Distillation Methodology & Architectural Reasoning

Sequence-Level Knowledge Distillation: In sequence-level KD (Kim and Rush, 2016), the compact student model (EleutherAI/pythia-70m) is trained via standard maximum likelihood estimation (autoregressive cross-entropy loss) directly on teacher-generated output sequences: $$\mathcal{L}_{\text{seq}} = -\sum_{t=1}^{T} \log P_S(y_t \mid y_{

Logit-Based Distillation: In logit-based (token-level) KD, the student minimizes the Kullback-Leibler (KL) divergence between its softened output probability distribution and the teacher's distribution at every token step: $$\mathcal{L}_{\text{logit}} = (1-\alpha)\mathcal{L}_{\text{CE}} + \alpha \tau^2 \mathcal{D}_{\text{KL}}\left(\sigma(z_T / \tau) \parallel \sigma(z_S / \tau)\right)$$

Why Logit-Based Distillation is Infeasible in this Project: Logit-based KD is fundamentally impossible here due to two architectural barriers: 1. Vocabulary and Tokenizer Discrepancy: The teacher model (Phi-3.5-mini) uses a SentencePiece tokenizer with a 32,064-token vocabulary. In contrast, the student model (Pythia-70M) utilizes a byte-level BPE tokenizer derived from NeoX with a 50,304-token vocabulary. Because output logit dimensions do not match ($32,064 \neq 50,304$) and underlying token boundaries differ, direct point-wise cross-entropy or KL divergence over logits is mathematically undefined without an arbitrary projection mapping. 2. Black-Box API Isolation: The teacher was served via Ollama's REST API (/api/generate), which returns only discrete decoded text tokens. Complete full-vocabulary probability distributions and unnormalized logits ($z_T$) are not exposed by standard containerized inference endpoints.

Inherent Limitation of Sequence-Level KD: The primary drawback of sequence-level distillation is exposure bias and error propagation. Because the student is trained purely on the teacher's static outputs under teacher-forcing, it receives no guidance regarding the uncertainty or alternative plausible interpretations present in the teacher's soft probability landscape. During autonomous inference, a single misplaced brace or token generation error can shift the hidden state into an out-of-distribution regime, causing catastrophic failure across subsequent tokens.

3. Task 3: The Inference Service in a Container

3.1 Microservice Architecture & API Implementation

The inference engine was authored using FastAPI in service/app.py, exposing three endpoints on port 8000:

  • POST /parse: Accepts {"text": ""}. Validates JSON payload, runs CPU token generation with Pythia-70M, parses the JSON structure, verifies adherence to schema.json, and returns HTTP 200 with the 4-key JSON object. Injects required HTTP response headers: X-Model-Version and X-Served-By (Pod hostname).
  • GET /healthz: Liveness probe endpoint returning HTTP 200 ({"status": "alive"}) as long as the process is alive.
  • GET /readyz: Readiness probe endpoint returning HTTP 503 ({"status": "not_ready"}) while model weights are downloading, switching to HTTP 200 ({"status": "ready"}) only after weights are loaded into memory and verified.

3.2 Model Loading & Security Secrets

All service configuration is injected via four environment variables: MODEL_URI (e.g. s3://models/v1/), MODEL_VERSION (v1), S3_ENDPOINT (http://seaweedfs.data.svc.cluster.local:8333), and MAX_NEW_TOKENS (100). During container startup, the service connects to SeaweedFS using S3 access credentials populated strictly from a Kubernetes Secret (inference-s3-credentials). It downloads model weights, validates the SHA-256 digest against model.sha256, and loads PyTorch weights into memory before accepting ingress traffic.

3.3 Validation & Fault Injection Testing

Model outputs are parsed with a robust balanced-brace parser and strictly validated against service/schema.json. If the model produces unparseable text or violates the four-key taxonomy, the endpoint intercepts the failure and returns HTTP 500 with {"error": "invalid_model_output"}. When environment variable FAULT_INJECT=1 is set, the service intentionally substitutes the model output with "not json" prior to schema verification, triggering an immediate HTTP 500 response. This was confirmed by automated unit tests in tests/test_service.py.

3.4 Container Optimization & Resource Constraint Verification

The container image (service/Dockerfile) was built on python:3.11-slim, installing CPU-only PyTorch wheels (--extra-index-url https://download.pytorch.org/whl/cpu) with all dependency versions strictly pinned. Model weights are completely excluded from the Docker image layers, resulting in an image size of 1.87 GB, safely below the 2.0 GB constraint.

5.2 Stateless NACL Rule Architecture & Theory

The NACL for the public subnet (where the load balancer resides) was declared in network/nacl.json: Inbound Rules: Rule 90: DENY all from 198.51.100.0/24 | Rule 100: ALLOW TCP port 80 from 0.0.0.0/0 | Rule 110: ALLOW TCP port 443 from 0.0.0.0/0 | Rule 120: ALLOW TCP port 22 from 10.20.5.128/27 | Rule 130: ALLOW TCP ports 1024–65535 from 10.20.0.0/22 | Rule 140: DENY all remaining inbound. Outbound Rules: Rule 100: ALLOW TCP port 8000 to 10.20.0.0/22 | Rule 110: ALLOW TCP ports 1024–65535 to 0.0.0.0/0 | Rule 120: DENY all remaining outbound.

Why a Stateless NACL Requires Explicit Reply Rules: Unlike stateful firewalls which track TCP connections, a Network ACL is completely stateless. When a client initiates an inbound TCP session to port 80, the return packet travels back towards the client's temporary ephemeral port (1024–65535). Because the NACL has no state table recording that this packet belongs to an established conversation, the reply is dropped unless an explicit outbound allow rule permits ephemeral traffic.

Why Rule Order Matters for 198.51.100.0/24: NACL evaluation is top-down using first-match-wins logic based on ascending rule numbers. If the block rule were placed at rule 150 (after allow rules 100 and 110), packets from 198.51.100.9 would match rule 100 (0.0.0.0/0) and be permitted, defeating the block. Placing the deny rule at Rule 90 guarantees that abusive packets are dropped before permissive rules are evaluated. Verification: tools/nacl_sim.py against network/packets_sample.jsonl: 6 / 6 = 100.0% Correct.

$$\text{Cost}_{\text{replica}} = (1 \times 3.50) + (1 \times 0.45) = ₹3.95 / \text{hour}$$ $$\text{Cost}_{\text{total}} = 2 \times 3.95 = \mathbf{₹7.90 / \text{hour}}$$ $$\text{Requests / hour} = 5.13 \text{ req/s} \times 3600 \text{ s} = 18,468 \text{ requests}$$ $$\text{Cost per 1,000 Requests} = \left(\frac{\text{Hourly Cost of Replicas}}{\text{Requests Served per Hour}}\right) \times 1000 = \left(\frac{₹7.90}{18,468}\right) \times 1000 = \mathbf{₹0.4278 \approx ₹0.43}$$
